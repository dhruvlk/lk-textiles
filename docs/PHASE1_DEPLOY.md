# Phase 1 deploy notes (data integrity and permissions)

Roadmap items: DATA-001, SEC-001, RPT-001, TECH-001. Branch `phase-1/data-integrity`.

## What changes for users

| Who | Before | After |
|---|---|---|
| Employee with **view-only** rights on a module | Could still create, edit or delete through the API | Writes are refused by the database |
| Employee with **create** rights | Could create, edit and delete | Can create; editing needs edit, deleting needs delete |
| Recording an **invoice payment** | Anyone who could open the invoice | Needs **Invoices → Edit** (button hidden otherwise) |
| Owners | Full access | Unchanged |
| Admin / Manager / Accountant with **no** permission matrix | Full access | Unchanged (decision K-1 default) |
| Reading any module's data | All members | Unchanged |
| Recording a **purchase payment**, closing a **financial year** | Any member | Needs **Purchases → Edit** |
| Uploading / deleting **vault documents** | Any member | Upload: Purchases create or edit · Delete: edit or delete |
| Changing **stock** outside invoices, challans and purchases | Any member (by calling the stock functions directly) | Needs **Stock → Edit** |

Other changes:

- Invoices, payments, delivery challans, purchases and stock edits save in one transaction: all or nothing.
- Reports, year-end, dashboard and reminders read every row, not just the first 1,000.
- Editing a stock quality's total works again (it failed on a database check before).
- A refused edit or delete now shows "You do not have permission to …" instead of a false "saved" / "deleted".
- Deleting a purchase bill whose stock has already been delivered is blocked with the reason, instead of a database error.

## Deploy order

1. Confirm `20261022000001_security_hardening.sql` is applied (roadmap OPS-001).
2. Review the employees' permission matrices in **Employees**. Anyone who must keep creating or editing needs those boxes ticked before step 4.
3. Apply `20261023000001_transactional_document_rpcs.sql` (staging first, then production). It only adds functions and widens one check constraint, so the current app keeps working.
4. Deploy the app. It now calls those functions.
5. Apply `20261023000002_module_permission_rls.sql`. It replaces the write policies; from here view-only employees can no longer write.
6. In Supabase, **Settings → API → Exposed schemas** must not include `private` (the default list is `public`, `graphql_public`). The raw stock functions live there now.
7. Smoke test with an Owner and one employee: create an invoice, record a payment, create and delete a delivery challan, edit a stock total, create a purchase bill with an initial payment, then record a second payment on it.

**Rollback:** each migration only adds functions, swaps policies and moves the two stock helpers into `private` (move them back with `alter function private.<name>(…) set schema public` after dropping the gates). To undo SEC-001, re-create the previous `Members can access …` `for all` policies (each one's name appears in the `drop policy` lines of `20261023000002_*`); to undo DATA-001, redeploy the previous app build (the new functions can stay), but only after undoing the stock-helper move as well: the old app calls those helpers directly.

## Tests you can run

| Command | What it checks | Needs |
|---|---|---|
| `npm test` | Unit tests | Node |
| `npm run test:db` | All migrations apply to a fresh database; transactional functions; permission matrix per role; concurrent payments | PostgreSQL 15+ superuser (`PGHOST`, `PGUSER`, …) |
| `npm run test:api` | App services → PostgREST → Postgres, incl. a 5,000-invoice report check | Same + `postgrest` on PATH |

CI (`.github/workflows/ci.yml`) runs all of them plus typecheck and build on every pull request. Lint runs but does not block yet (TECH-005).

The database tests stub Supabase's `auth` and `storage` schemas (`supabase/tests/00_supabase_stub.sql`). They never touch a real project.

## Still open after Phase 1

- `notifications` rows can still be inserted, marked read or deleted by any member of the company (low risk: they are generated by the app itself).
- `20260923000001_salary_slips.sql` gained a `DROP FUNCTION IF EXISTS` so a fresh database can be built from the migrations; production already ran it, so nothing changes there.
